# CWパイルアップ対応：1局選択型受信・交信制御（Rev.A v0.3.1／設計仕様）

更新日：2026-11-05

## 目的と要求レベル

JARL国内コンテストのRUN運用（自局がCQを出し、複数局から呼ばれる場合）において、**全呼出局を同時に解読することは要求しない**。混信中の受信音声から**交信成立の見込みが最も高い1局**を選択し、その局のコールサインとコンテストナンバーの交換を確実に完了する。

最適化目標は「全局同時デコード数」「重畳信号の完全分離」ではなく、(1)誤コールサイン応答率の低さ、(2)有効QSO成立率、(3)成立QSO/分、(4)誤ったログ確定の防止である。特に、コールサインが曖昧な状態で確定したかのように応答しない。厳密に分離できない音があることを前提とする。

## ハードウェア境界

- 初代IC-7300（IC-7300M/Sを含む）のUSB AF入力をWindows PCで取り込む。
- 外部CW分離基板・SDR・追加音声インターフェースはRev.A標準構成に含めない。
- 送信は無線機内蔵CI-V CW文字送信 `17h`。既存の送信デフォルト禁止と承認ゲートを変更しない。
- IF帯域・AFフィルタ・運用上の受信可能帯域を超える局を全数追うことはしない。

## DeepCW技術の調査結果と採用判断（2026-11-05時点）

公式公開元：
- Web UI: https://github.com/e04/web-deep-cw-decoder
- Python/Node.js用エンジン: https://github.com/e04/deepcw-engine
- 作者の解説: https://zenn.dev/e04/articles/1408d7b03d78cb

確認した公開事実：
- ニューラルネットによるCW復号。Web UIにはSINGLE/MULTI表示・複数CW信号の検出機能がある。
- `deepcw-engine`はONNXモデルとWAV入力のPython/Node.js最小実装例を配布する。
- 通常モデル `model.onnx` に加え、多チャンネル向け軽量狭帯域モデル `model_narrow.onnx` が存在する。
- 公開READMEではモデルメタデータを参照すること、通常モデルのWAV入力例はmono PCM 3200 Hzであることが示される。
- 現行のエンジンリポジトリの `LICENSE` はMIT（リポジトリ更新で変わり得るので実際に採用するコミットを固定して再確認する）。

未確認事項：
- 外部アプリが利用できる安定した**ライブストリーミングAPI**の存在、フレームごとの信頼度の取得方法。
- IC-7300の通常USB AFで、同一ピッチ・同タイミングの多局重畳に対してどの程度コールを正しく取り出せるか。
- Windows実機上での遅延と負荷、コンテスト運用下の実データ精度。

採用方針：DeepCWエンジンを**復号バックエンドの第一評価候補**とする。Webアプリをそのまま操作して交信を自動化するとは限らない。組込みの可否・ライセンス・API・性能を検証したうえで、デコーダー・アダプタとして交換可能に実装する。現行の `audio_cw.py`（単一信号Goertzel復号）は回帰テスト用として維持し、削除しない。

## 処理パイプライン（予定）

1. `USB_AF_CAPTURE`: USB音声をタイムスタンプ付き短時間リングバッファへ取得する。
2. `CW_DECODE_ADAPTER`: DeepCW等の復号器から文字列候補、音響上の追跡情報、デコーダーが実際に提供する品質指標を受ける。単一デコードしか得られない場合でもよい。APIが提供しない信頼度はでっち上げない。
3. `CALL_CANDIDATE`: コンテスト用コールサイン構文に適合する候補を抽出。部分コピーを維持する。`?`を含む文字列は未確定として扱う。
4. `CANDIDATE_SELECTOR`: 有効な候補から一局選択。交信成立の見込みを最優先とし、完全に受信できない局は探索を続けない。
5. `TARGET_LOCK`: 選択局の識別情報・タイムスタンプ・受信特徴を保持。応答を開始したら、他局の符号をナンバーとして混入させない。
6. `QSO_FSM`: 既存の承認付き交信状態機械に候補を渡す。再送要求・中断は交信制御側が決める。
7. `LOG`: 正しく交換できた局のみ記録し、重複・得点判定は既存JARLロギング処理へ渡す。

## 取捨選択ルール

- 最優先は**コールサインの確からしさ**。音が大きいだけでは採用しない。
- 次点は継続性（同一コールサインの反復、同じ局とみられる音程や速度の連続性）、非重複局であること、コンテスト進行の容易さ。
- 未交信局と既交信局が同等の明瞭度なら未交信局を優先する。ただし新マルチを推測して誤コピーの危険を取らない。
- 同じ瞬間の複数デコード候補はあくまで**候補**。実際の同時送信局数とは一致しない可能性がある。
- 強さ・トーン・WPM・コールサイン文法はあくまで補助情報。確認できないコールを外部コールサインDBから補完して確定扱いにしない。
- 1局を選択した後の他局からの割込みを受信ナンバーとして扱わない。選択対象の識別が破綻したら未確認状態へ戻す。

## パイルアップ交信フロー

`CQ_TX -> WAIT_CALL -> CANDIDATE_COLLECTION -> SELECT_ONE -> [MANUAL_APPROVAL] -> SEND_CALL_AND_EXCHANGE -> WAIT_REPLY -> CHECK_IDENTITY_AND_EXCHANGE -> ACK_OR_AGN -> LOG_COMPLETE -> CQ_TX`

分岐：

- `候補が0`: 自局のCQ再送または受信継続（送信間隔の安全条件を守る）。
- `候補はあるが全て曖昧`: 無理に応答せず再送待ち。部分コピーが十分で、周囲の別局を誤指定しにくい場合のみ部分指定で確認を求める。
- `候補が複数`: その中の1局だけを選択し、他局は今回のQSOでは扱わない。
- `相手の応答が識別できない`: `AGN?`／`NR?`等、必要部分を再送要求する。再送上限・タイムアウトを超えればQSO不成立で終了し、次の局に進む。
- `相手コールと選択候補が不一致`: 自動確定せず再確認。異なる局のナンバーを混ぜない。
- `重複局と判明`: 交信をした場合はJARLルールに従ってログに残し、得点対象外として計算する。
- `送信中断・CI-V障害・想定外のTX継続`: 送信停止要求とオペレーターへの通知を行い、停止確認できなければ自律再開しない。

## 受信性能の評価計画

測定対象は受信機・USB AF・復号器・候補選択・QSO制御までを含む**システム全体**。合成音声だけのベンチマークと実機運用を区別する。

| ケース | 検証入力 | 合格の考え方 |
|---|---|---|
| A | 明瞭な1局 | コールサインとナンバーを誤確定せず受け取る |
| B | 異なるピッチの2局 | 両局解読を必須にせず、少なくとも1局とのQSOが安全に成立する |
| C | ほぼ同一ピッチ・異WPMの2局 | 片方の局を継続追跡、困難なら再送/保留できる |
| D | 完全に重なった判別困難な信号 | 内容を捏造せず、保留・再送・中断を選択する |
| E | 弱信号・QSB・QRM | 正解できるときだけ採用。不確実なコピーは確定しない |
| F | 既交信局と新規局の同時呼出 | コピー精度を維持し、同等条件なら新規局を選ぶ |
| G | 応答後に別局が送信 | 他局のナンバーが選択局の記録へ混入しない |

定量評価するメトリクス：候補正解率、**誤呼出率**、QSO成立率、1QSO当たり時間、QSO/分、再送要求率、誤ログ確定数、実時間処理遅延、CPU負荷。初期閾値は実データ測定前に固定しない。
